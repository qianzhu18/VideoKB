# 向量数据库迁移决策与过程记录

状态：`active`
最后复核：2026-10-19

## 决策摘要

- **目标方向已确认：**2026-10-09 确定后续优先使用 Milvus，2026-10-17 再次确认最终切换方向。Milvus 是目标 dense 向量库；Qdrant 是迁移期间保留的现行库。
- **实施状态：尚未完成 dense 迁移。**当前 dense 写入/查询仍由 Qdrant 承担；Milvus 仅有可显式启用的 BM25 词法通道。双写、dense 回灌、影子查询、灰度切读都还没有实现。
- **这是一项目标栈决策，不是已证实的性能结论。**当前数据没有显示 Qdrant 已达到容量或性能瓶颈，也没有同条件 Qdrant dense vs Milvus dense 基准，不能声称迁移已带来提速、降本或召回率提升。
- **本文件是迁移理由、目标、阶段和过程证据的唯一决策日志。**代码架构与当前实线/迁移虚线见[向量库架构与迁移边界](向量库架构与迁移边界.md)；具体实验数字仍以各版本报告为准。

## 为什么迁移

### 已确认的决策原因

负责人明确指定 Milvus 为后续优先技术栈，并在 2026-10-17 确认最终切换方向。这是迁移工作的直接决策依据。原有系统和当前代码使用 Qdrant 是历史实现事实，不代表 Qdrant 曾在同条件评测中胜出。

### 技术上希望解决的问题

1. **收敛向量基础设施。**当前 dense 在 Qdrant；可选 BM25 词法索引在 Milvus；默认关键词又在 MySQL。把 dense 迁至 Milvus 的目标，是让 dense 与 BM25 可以在同一向量数据库技术栈下维护，减少双库索引状态、运行环境和故障排查的分散。是否能减少实际运维成本，要由迁移后的运行数据验证。
2. **统一 dense 与词法检索的演进路径。**Milvus 已有本项目原生 BM25 写入、查询、generation 对账和降级实现，且产品支持 dense 检索。目标是在保留 dense 与词法两路召回契约的前提下，评估同一后端承载的 collection/schema 与运行方式；不是把两路排名、权限或证据校验塞进数据库。
3. **建立清晰可替换的存储边界。**当前 `KnowledgeVectorIndex` 只抽象查询，索引写入仍直接依赖 Qdrant。迁移要求补齐 upsert/query/delete 契约，使后续换库不再散落修改索引编排和检索逻辑。

### 这些不是迁移理由

- 2026-10-08 的严格证据集暴露了检索质量缺口，但结果不能归因于 Qdrant ANN 实现；换库本身不保证找全跨视频证据。
- 2026-10-09 的 BM25 词法实测比较的是 Qdrant dense、MySQL LIKE、Milvus BM25 与应用层 RRF，并没有测试 Milvus dense。
- 2026-10-17 的 Milvus standalone 启动和内存观察说明本机实验形态可运行，不代表生产规模、HA、吞吐或 SLA 已验证。
- 因此不能把迁移描述成修复了 Qdrant 缺陷、必然更快、必然更省，或必然提高问答质量。

## 迁移目标与成功条件

| 目标 | 具体要求 | 成功证据 |
| --- | --- | --- |
| 后端收敛 | Milvus dense 成为目标 dense 后端；BM25 词法通道继续可独立评估；迁移期间允许双写 | 配置与代码明确区分 dense/lexical collection，写入、查询、删除都经稳定端口 |
| 数据可迁移 | 新旧索引使用相同 owner/source/version、embedding model、dimension、profile 和证据 ID 契约 | 回灌可重跑、计数/身份对账完整；新版本失败不影响旧 READY 版本 |
| 权限可信 | MySQL 继续作为 owner、placement、原文、发布版本的权威来源；向量库 payload 不能授予访问权限 | 跨用户、撤权、移动目录、删除来源、旧版本查询用例全部通过 |
| 质量可比较 | 固定原文、块、embedding、query、scope、topK 与词法/RRF 策略后比较新旧 dense 后端 | 预先冻结的问题集和门槛；必要证据覆盖不退化，分别报告检索质量和数据库性能 |
| 故障可恢复 | 灰度期间保留 Qdrant 回退；校验 Milvus 停机、部分写入、删除、重启、回滚 | 故障注入和恢复报告证明查询范围、版本指针与索引数据一致 |
| 运行可接受 | 测带过滤 P50/P95、吞吐、资源、部署复杂度和维护成本 | 同环境、同负载的可复现对照；无数据前不写收益百分比 |

**业务成功不等于“Milvus 能启动”或“数据写进去了”。**必须同时满足数据一致性、授权边界、质量门槛、故障恢复和可回滚条件。MySQL 仍是业务事实源，Milvus 只是索引存储。

## 业务依据

学生需要跨视频找全依据、准确回看、资料更新失败时继续查旧版、在 Web/MCP 使用相同范围。这些要求主要依赖原文/检索块分离、版本发布、授权过滤、词法召回、融合重排和结论校验。向量库是候选召回基础设施，不能独自完成上述业务契约。

[开发集基线](../../eval/reports/evidence-baseline-dev-20261008.json)显示 dense 必要片段 Recall@8 约 89.5%，当前 LIKE+RRF 约 68.4%，关键跨视频题未找全。不能由此归因 Qdrant 的 ANN 性能，也不能据此证明切换 Milvus 会改善结果。首先固定数据/索引 profile 并补齐完整检索流程。

## Embedding 与元数据契约

Embedding 模型决定向量空间和维度，数据库负责存储/检索。当前 BAAI/bge-m3 的 dense 输出为 1024 维，见 [模型说明](https://huggingface.co/BAAI/bge-m3)。4096 维不天然更准确。更换模型必须记录模型、维度、分块 profile、归一化与距离度量，重新建相应索引，不能混用不同模型空间。

MySQL 保存原文时间窗、source/版本、目录引用和块到原文映射；向量库保存向量与 user/source/indexVersion/检索块 ID 等过滤 payload。检索后回查原文并再次授权。内容多目录归属增加 placement，不复制同内容向量。标题、创建时间、顺序、模型/profile 应有权威记录；向量 payload 不是目录权限的唯一事实源。

## 迁移门槛

独立 `experiment/milvus-comparison` 使用相同原文、块、Embedding 模型和向量、授权条件、topK、问题及冷热/混合负载。分别比较 ANN 证据覆盖、带过滤 P50/P95、索引与更新吞吐、删除可见性、故障恢复、资源占用及运维成本。只比较完整 RAG 结果时须固定词法与重排实现，避免把策略变化说成库差异。

依照最新偏好推进 `feat/milvus-migration`；同条件实验用于确认性能边界与迁移配置。切流前：通过统一写入/查询/删除接口，双写、完整回灌、影子查询与授权一致性对账，保留 Qdrant 回退；灰度切流后验证删除和版本边界。现有 `KnowledgeVectorIndex` 只抽象查询，写入仍依赖 Qdrant，尚不能宣称任意向量库可替换。社区共享与生产切流不因实验完成而自动获准。

## 首批词法实现（2026-10-09）

已实现可显式启用的 Milvus 原生 BM25，当前 13 课程/592 块的词法回灌、授权/版本过滤、降级与重启恢复在隔离环境验证。真实开发集证明 BM25 相对 LIKE 的词法增益，但 dense 仍优于 RRF；这是词法策略对照，不是两个库 dense ANN 性能对照。完整 dense 写入/删除抽象、双写、影子查询和生产迁移尚未完成，Qdrant 数据保留。见 [实现与证据](词法召回与对照-2026-10-09.md)。
